### 3. Current RLS Policies (❌ PROBLEM IDENTIFIED)

**File**: `SQL_APPOINTMENTS_PAYMENT_ORDERS_SCHEMA.sql` (lines 78-128)

#### Current SELECT Policy:
```sql
CREATE POLICY "Authorized users can view all payment orders"
  ON public.payment_orders
  FOR SELECT
  USING (
    auth.uid() IN (
      SELECT user_id FROM public.users WHERE role IN ('admin', 'comptable', 'gestionnaire')
    )
    OR auth.uid() = user_id
  );
```

**Problems**:
1. **Subquery-based check** - `SELECT user_id FROM public.users WHERE role IN (...)`
   - Can timeout on Supabase
   - Can fail if user doesn't exist in public.users
   - Requires extra database lookup on every query

2. **Restrictive condition** - Only allows specific roles
   - If user not in public.users table with correct role, access denied
   - No fallback for authenticated users

3. **Unreliable on Supabase** - Supabase REST API has issues with:
   - Complex RLS conditions
   - Subqueries in USING clauses
   - Cross-table policy checks

#### Current INSERT Policy:
```sql
CREATE POLICY "Authorized users can create payment orders"
  ON public.payment_orders
  FOR INSERT
  WITH CHECK (
    auth.uid() IN (
      SELECT user_id FROM public.users WHERE role IN ('admin', 'comptable', 'gestionnaire')
    )
  );
```

**Problem**: Same subquery-based issue - fails with 403

#### Current UPDATE & DELETE Policies:
Same issue - using restrictive subquery checks

#### Missing bons_commandes SELECT Policy:
```
❌ No SELECT policy on bons_commandes table
```
**Result**: Dropdown search fails with 403 Forbidden

### 4. Root Cause Analysis

| Issue | Why It's a Problem | Impact |
|-------|-------------------|--------|
| Subquery in USING clause | Supabase REST API doesn't reliably handle complex RLS | 403 Forbidden on all queries |
| Role check from external table | Requires user to exist in public.users with matching role | User gets blocked even if logged in |
| No public.users row | User in auth.users but not in public.users | RLS subquery returns empty, auth.uid() NOT IN () |
| Missing bons_commandes SELECT | No permission to read dropdown data | Dropdown search fails |
| Cross-table dependency | RLS policy depends on another table's data | Single point of failure |

**Real Cause**: The comptable user is logged in (in auth.users) but either:
1. Not in public.users table, OR
2. In public.users but with different role, OR
3. The subquery is timing out

## ✅ SOLUTION IMPLEMENTATION

### 1. Root Cause of 403 Error

The 403 error is caused by **overly restrictive RLS policies** that check user roles via subquery:

```sql
-- CURRENT (FAILS):
WHERE auth.uid() IN (SELECT user_id FROM public.users WHERE role IN ('admin', 'comptable', 'gestionnaire'))

-- The subquery returns no results if:
-- - User not in public.users table
-- - User role != 'admin', 'comptable', 'gestionnaire'
-- - Subquery times out or fails
```

### 2. Proposed Solution

Replace restrictive subquery-based policies with simple authentication-based policies:

```sql
-- NEW (WORKS):
USING (auth.role() = 'authenticated')

-- This allows ALL authenticated users:
-- - No subquery needed
-- - No external table dependency
-- - Reliable on Supabase
-- - Still requires user to be logged in
```

**Trade-off**:
- **Less Restrictive**: Anyone logged in can see/edit/delete ANY payment order (not just their own)
- **More Reliable**: No 403 errors, works on Supabase
- **Acceptable Risk**: Company ERP system where all users are trusted employees
- **Alternative**: Could add row-level filtering later with additional checks
